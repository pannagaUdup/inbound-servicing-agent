Agentathon · inbound-servicing-agent

Inbound WhatsApp servicing agent: detailed architecture

The agent resolves routine borrower requests and routes the rest with full context. LLMs handle perception, planning and wording. Code makes every decision with consequences: verification, account scope, payment acceptance, routing and approvals. File paths refer to src/servicing_agent/ in the repo.

T1 Agent core and guardrails T2 Platform, integrations, human approval T3 Data, perception, evaluation built stub planned

Verification

The account number plus the sender's registered mobile number, then OTP. A customer can have several numbers, and a number can belong to more than one customer, so the mobile number is never used to look up an account on its own.

  participant L as LMS
  participant O as OTP service
  B->>G: "what is my foreclosure amount"
  G-->>B: "Please share your loan account number"
  B->>G: CN5757705297
  G->>G: format check, CN plus 10 digits, Luhn
  G->>L: active_contact_for(account, sender)
  alt sender is an active contact on the account
    L-->>G: contact_id, customer_id, added_on
    G->>O: send OTP to sender
  else no match
    L-->>G: none
    G->>G: failed_attempts plus 1, no OTP sent
  end
  G-->>B: "If the details match our records, you'll receive an OTP"
  B->>G: 6-digit code
  alt code valid
    G->>G: AuthScope set, expires after 30 min idle
    G-->>B: runs the saved foreclosure task
  else third wrong code
    G->>G: lock for 30 min
    G-->>B: "We couldn't verify these details"
  end

Policy gateway and output guard

These two components enforce the zero-tolerance criteria in code, so the result doesn't depend on how the prompt behaves.

flowchart LR
  H["Handler"] -->|"intent, args
never account_id"| GW{"scope set?"}
  GW -- no --> DEN["TOOL_DENIED event
NotVerified raised"]
  GW -- yes --> CALL["tool(scope.account_id, args)"]
  CALL --> F["filter to config/intent_fields.yaml"]
  F --> LED["record values in
allowed_numbers, allowed_strings"]
  LED --> H2["handler fills template"]
  H2 --> OG{"output_guard"}
  OG -- "commitment wording" --> BLK["OUTPUT_BLOCKED
safe_fallback sent"]
  OG -- "other account number or mobile" --> BLK
  OG -- "amount, date or UTR not in ledger" --> BLK
  OG -- "unverified and any account value" --> BLK
  OG -- pass --> SEND["reply sent"]
The output guard removes URLs, allowed strings and the helpline number. It then parses every remaining number. Small counts under 100 pass. Anything else must be in this turn's ledger, or the message is replaced.

The borrower always gets a neutral message ("we couldn't match this yet, our team is reviewing it"). The SUSPECTED_MISMATCH flag appears only on the internal ticket. Dunning suppression on MATCHED is parked.

Waiver and settlement cases

The agent creates requests and reports their status. It never predicts an outcome, calculates an amount, or words a decision itself. A material change restarts the whole review.

sequenceDiagram
  autonumber
  participant B as Borrower
  participant G as Agent
  participant C as Case service
  participant DB as Postgres
  participant A as Approver
  B->>G: "waive penal charges, Rs 5000"
  G->>C: create(scope account, request)
  C->>DB: insert v1 PENDING_APPROVER, etag e1
  G-->>B: "Submitted, reference CASE-123"
  B->>G: "make it Rs 3000"
  G->>G: compare fields with v1, material change
  G-->>B: "Change 5,000 to 3,000? This restarts the review"
  B->>G: Yes
  G->>C: supersede(case, from v1, new request)
  C->>DB: one transaction, v1 SUPERSEDED where etag e1, insert v2 with diff
  G-->>B: "Updated request submitted"
  A->>C: decide(v1, etag e1, approve)
  C->>DB: update where version 1, PENDING_APPROVER, etag e1
  DB-->>C: 0 rows
  C-->>A: 409 superseded

Scale to 500 concurrent conversations

  • About 2–10 messages per second at peak
  • Workers: 4 pods × 100 async tasks, HPA on queue lag
  • The real limit is LLM tokens per minute: token bucket per provider, failover
  • LMS reads cached for 60 s; config held in memory
  • Independent tool calls run with asyncio.gather

Security and compliance

  • Webhook HMAC; mTLS or IAM for internal tools; secrets in AWS Secrets Manager
  • PII masked before LLM calls and traces
  • S3 with SSE-KMS, 90-day media retention, signed URLs
  • PDFs password-protected with the borrower's DOB
  • DPDP: purpose limitation, retention, STOP honoured
  • RBI fair practices: a human for every harassment complaint

Alerts

  • p95 first response over 20 s for 5 min
  • Queue over 200 messages or lag over 60 s
  • Tool error rate over 2% for 5 min
  • Any OUTPUT_BLOCKED disclosure pages on-call
  • Injection events per hour over 3σ
  • Cost per conversation 30% above the 7-day baseline
