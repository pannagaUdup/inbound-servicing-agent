1 · System architecture

  • Ingress only acknowledges and enqueues. The work runs on workers, so the webhook stays under 100 ms.
  • The per-conversation lock keeps messages in order. Messages sent within 3 s of each other are processed as one turn.
  • Voice and image turns get a holding reply in under 3 s, which keeps the first response well inside the 30 s target.
  • Waiver and settlement decisions arrive through the case API. They resume an approval thread only if that request version is still current.

2 · End-to-end message sequence

  • Total latency: about 0.1 s ingress, 1–2 s holding reply, 2–4 s ASR, about 1 s plan, under 1 s tools, 1–2 s compose and guard.
  • Every step writes an audit event. The dashboard and the evaluation harness read the same events.

3 · Conversation graph (LangGraph)

  • Distress, legal threats and harassment skip planning and go straight to a human.
  • Detected injections are logged and only the legitimate part of the message is handled. The bot never says it noticed the attack.
  • Low confidence gets one clarifying question. If the borrower is still unclear, the conversation is routed.

4 · Verification: account number + mobile + OTP

  • A session covers one account. Asking about another loan means verifying it, which replaces the scope.
  • Lockouts: 3 OTP attempts, 5 failed account numbers per sender per 24 h, and 3 or more numbers failing on one account.
  • A contact added in the last 7 days gets a SIM-swap flag, so documents and waivers need a human check.

5 · Payment-claim reconciliation

  • A receipt can only be generated from a D7 txn_id. The tool doesn't accept a free-text amount.
  • Edited and reused proofs go to the Fraud queue with a field-by-field diff. The borrower gets a neutral reply.

6 · Waiver / settlement case states

  • A material change is a code diff on type, amount, components, plan or reason, and the borrower must confirm it.
  • Status checks, new evidence and duplicate messages don't restart the flow.
  • If the borrower changes a request after an offer was sent, the case is flagged offer_outstanding and compliance decides what the borrower is told.

7 · Supersession and stale-approval guard

  • Each version runs on its own LangGraph thread (case:{id}:v{n}), paused with interrupt() and resumed only through the version-checked decision API.
  • Approver and compliance both receive the context pack: loan position, payment history, policy band, version diffs, risk flags, compliance checklist and transcript.

8 · Evaluation and CI loop

  • Must-be-zero metrics: disclosure before verification, cross-account data, commitments, fake payments accepted, numbers not backed by a tool, approvals on stale versions.
  • Targets: ≥ 70% resolved without a human, ≥ 95% routing accuracy, p95 first reply under 30 s at 750 users.
